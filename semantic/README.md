# Semantic Layers

Human-reviewable business definitions, as local Markdown files, for the databases exposed by the `semantic-sql` MCP server. There is **one semantic layer per dataset**, in its own directory. (These have nothing to do with warehouse catalogs such as Databricks Unity Catalog.)

Agents: call `list_tables` first — it reports the active semantic layer directory (set by `SEMANTIC_DIR` in `.env`). Read it **before** writing SQL. Prefer `approved` definitions and say when you rely on a `proposed` one. Write SQL in the dialect reported by `list_tables`.

## Datasets

| Directory | Database | Contents |
| --- | --- | --- |
| `demo/` | SQLite (`demo/seed.sql`) | Demo `customers` and `orders` |
| `harbourstone_financial/` | Databricks (catalog set by `DATABRICKS_CATALOG`) | Schemas `retail_banking`, `commercial_banking`, `insurance` |

## Layout of a semantic layer

| Path | Contents |
| --- | --- |
| `entities/<table>.md` | One file per entity: table, primary key, columns, relationships, open questions. Use `<schema>.<table>.md` when `list_tables` shows schema-qualified names. |
| `metrics.md` | Metric definitions with SQL expressions |
| `glossary.md` | Business terms and their meaning |
| `examples.md` | Example questions with SQL |

A semantic layer is generated by running `/generate-semantic-layer`, which follows [`prompts/generate-semantic-layer.md`](../prompts/generate-semantic-layer.md), then reviewed by a human in Git.

## Rules

- Always include the **physical** table and column names in backticks, exactly as `list_tables` shows them (e.g. `retail_banking.gold_daily_deposits`).
- Every definition has a `Status:` of `proposed` or `approved`.
- Everything generated starts as `proposed`. Only humans change it to `approved`.
- Keep descriptions concise. Record ambiguities under an **Open questions** heading.
- Record sensitivity stated in column comments (e.g. `PII: email`) in the column description.
- **Never copy personal or sensitive data values** (names, emails, phone numbers, dates of birth, tax/ID/card/account numbers, free-text notes) into the semantic layer. Describe columns instead. Low-cardinality code values (e.g. `status`, `segment`) are fine.
- No credentials or connection details.

## Entity format

```markdown
# Order

- **Status:** proposed
- **Table:** `orders`
- **Primary key:** `id`

A purchase made by a customer.

## Columns

| Column | Description | Status |
| --- | --- | --- |
| `id` | Unique order identifier | proposed |

## Relationships

- `orders.customer_id` -> `customers.id` — each order belongs to a customer.

## Open questions

- Which values can `status` take?
```

## Metric format

````markdown
## Revenue

- **Status:** proposed
- **Definition:** Revenue from completed orders. Cancelled orders are excluded.

```sql
SUM(orders.total) -- WHERE orders.status = 'completed'
```
````

## Example format

````markdown
## What was revenue last month?

- **Status:** proposed

```sql
SELECT SUM(total) FROM orders WHERE status = 'completed' AND ...
```
````
